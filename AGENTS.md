# UniFood: правила для агента

Этот файл читает OpenCode в начале каждой сессии. Правила обязательны для всех трёх разработчиков.

## О проекте

UniFood: учебное веб-приложение для предзаказа еды в столовых и кафе ГрГУ с самовывозом. Роли пользователей: студент, сотрудник, администратор. Полный список функций и распределение задач смотри в `README.md` и `UniFood_roles.md`.

Проект делают три студента CS. Код должен быть написан в студенческом стиле: простой и читаемый, без лишних абстракций, паттернов и «умных» приёмов. Должно быть видно, что проект создавали студенты.

## Стек

- Frontend: HTML5, CSS3, JavaScript (без фреймворков и сборщиков)
- Backend: PHP (без фреймворков)
- Реляционная БД: MySQL
- Нереляционная БД: MongoDB
- Запуск: Docker (`docker compose`)

Не добавляй библиотеки, фреймворки и сервисы, которых нет в этом списке, без явного разрешения пользователя.

## Структура проекта

```
docker/php/Dockerfile     образ PHP + Apache
database/init/            SQL-скрипты для первого запуска MySQL
public/                   корень веб-сервера (страницы, css/, js/, api/)
src/                      общий backend-код (config, подключения к БД, сессии, роли)
docker-compose.yml
composer.json
.env.example              пример настроек (реальный .env в репозиторий не попадает)
```

Backend-код, который не должен быть доступен из браузера, лежит в `src/`, а не в `public/`.

## Как писать код

- **Комментарии как в реальной разработке.** В начале каждого файла: назначение файла. У каждой функции: документирующий комментарий (для PHP формат PHPDoc) с описанием, параметрами и возвращаемым значением. Внутри кода комментируй, **почему** так сделано, а не пересказывай очевидное. В `Dockerfile` и `docker-compose.yml` комментируй нетривиальные настройки.
- Язык комментариев: русский.
- Имена переменных, функций, файлов и папок: английские, понятные.
- Обращения к MySQL только через подготовленные запросы (PDO). Пароли и ключи не записываются в код и не попадают в репозиторий.
- Роли пользователей называются `student`, `staff`, `admin` везде одинаково.
- Не пиши лишнего: делай только то, что просит пользователь в текущей задаче.

## Git и GitFlow

- Работай только в ветке текущей задачи (`feature/...`), созданной от `develop`. Какая ветка нужна, говорит пользователь.
- Pull Request всегда открывается с базой `develop`. База `main` — только для релизов и хотфиксов; если PR случайно нацелен на `main`, поменяй базу до ревью (`gh pr edit <номер> --base develop`).
- Ветки `main` и `develop` не меняются прямыми коммитами: только через слияние одобренного Pull Request.
- `git push`, создание Pull Request и слияние одобренных PR разрешены, если пользователь дал на это явное указание в текущей сессии. Без такого указания ничего не отправляй и не сливай — это делает пользователь сам.
- Коммиты делай локально, небольшие и по смыслу (одна законченная часть работы: один коммит). Сообщения коммитов на русском, понятные.
- Не коммить `.env`, `vendor/`, служебные файлы системы и редакторов.

## Границы работы

- Делай только то, что указано в задаче. Ничего не добавляй «заодно».
- Не правь файлы, которые не относятся к задаче. Если для задачи нужно изменить чужой файл (общий код, общие стили, схему БД), остановись и спроси пользователя.
- Если требование неясно или противоречит этому файлу, не угадывай. Остановись и задай один уточняющий вопрос.
- Не удаляй и не переписывай существующий код без явной просьбы.

## Порядок работы над задачей

1. Сначала составь план действий и жди одобрения пользователя. Код не пиши.
2. После одобрения реализуй задачу по частям, после каждой части делай локальный коммит.
3. Проверь результат запуском в Docker. Если проверить нельзя, прямо скажи об этом. Не выдавай непроверенное за проверенное.
4. В конце выведи отчёт: что сделано, какие файлы созданы или изменены, результат проверки, в чём не уверен. Затем остановись и жди указаний.

|---|---|---|

### Корзина (контракт для `feature/cart`)

- Корзина хранится в сессии: `$_SESSION['cart']` — массив `[id блюда => количество]`, максимум 99 порций на позицию.
- Функции корзины лежат в `src/cart.php`: `getCart()`, `getCartItemCount()`, `addToCart()`, `updateCartQuantity()`, `removeFromCart()`, `clearCart()`.
- Страница корзины — `/cart.php`, доступна только после входа. Кнопка «В корзину» на страницах каталога отправляет POST на `/cart.php` с полями `csrf_token`, `action=add`, `dish_id`. Количество не передаётся: добавляется одна порция, повторное нажатие увеличивает количество.
- В корзине хранятся только id блюда и количество; названия и цены страницы берут из таблицы `dishes` (так делает `/order.php`).

### Оформление заказа (контракт для `feature/order-create`)

- Backend — `src/order.php`, страница — `/order.php`, доступна только после входа (`requireLogin()`).
- Состав и количество заказа всегда берутся из `$_SESSION['cart']`. Из формы приходят только `csrf_token`, `venue_id`, `slot_id`; состав, количество и цены из формы не принимаются.
- Цена каждого блюда копируется из `dishes.price` в `order_items.price`, `orders.total_price` считается по цене из БД.
- Слоты: активные и на будущее время; занятость — `COUNT(*)` по `orders.slot_id` без `status = 'cancelled'`. Проверка вместимости идёт в транзакции с `FOR UPDATE` по строке слота.
- Все блюда корзины должны быть доступны (`is_available = 1`) и относиться к выбранному заведению, иначе заказ не создаётся.
- Заказ создаётся одной транзакцией (`orders` + `order_items`), статус по умолчанию `new`. После успеха корзина очищается и страница переходит на `/order.php?success=<id заказа>` (повторная отправка формы второй заказ не создаёт).

### Смена статуса заказа и запись в Mongo (контракт для `feature/staff-orders`)

Ответ на вопросы Разработчика 1 из его запроса по С12–С13 — подтверждено, без изменений:

- `order_status_history.order_id` — `int` (значение `orders.id`), не строка;
- `changed_at` — `MongoDB\BSON\UTCDateTime`, не строка и не `DateTime`;
- один документ на одно изменение статуса: повторная отправка формы или двойной клик не должны создавать дубль (проверять, например, через подавление повторной отправки, как в `src/order.php`);
- `old_status` при записи — это значение `orders.status` непосредственно перед обновлением, не то, что пришло из формы;
- `changed_by` — `(int) $_SESSION['user_id']` сотрудника, который меняет статус, не email и не имя.

Переходы статусов (`orders.status`):

```
new → confirmed → ready → completed   (только вперёд, откатов назад нет)
new → cancelled
confirmed → cancelled
```

`ready` и `completed` в `cancelled` не уходят — после выдачи или готовности отменять поздно. `completed` и `cancelled` — конечные статусы, дальше `orders.status` не меняется. Любой другой переход `src/staff_orders.php` должен отклонять с понятной ошибкой, не молча игнорировать.

Порядок записи при смене статуса: сначала `UPDATE orders` (источник правды для сотрудника и студента), затем insert в `order_status_history`. Если запись в Mongo не удалась — статус в MySQL не откатывать: `error_log()` и сообщение сотруднику «статус обновлён, но запись истории не сохранена». Блокировать работу сотрудника из-за временной недоступности Mongo хуже, чем временно потерять одну запись истории.

PR #16 (`feature/order-status-history`) и #17 (обновление `AGENTS.md`) проверены задним числом — проблем не найдено, ревью подтверждено.

Реализация: `src/staff_orders.php` (`isValidStatusTransition()`, `getStaffVenueId()`, `listOrdersForStaff()`, `getOrderForStaff()`, `changeOrderStatus()`) и `public/staff/orders.php` (список заказов своего заведения с фильтром по статусу, детали с составом, форма смены статуса — в выпадающем списке только разрешённые следующие статусы). Сотрудник сам — работник конкретного заведения (кассир/повар на выдаче, без доставки), поэтому все функции фильтруют по `venue_id` из `users.venue_id`, а не показывают заказы всех заведений.

### Импорт меню с market.grsu.by (контракт для `feature/menu-import`)

- Заведения, участвующие в импорте, — только эти два, новые без согласования не создавать: «Столовая Главного корпуса» (`menu_sources.source_name = '1.
