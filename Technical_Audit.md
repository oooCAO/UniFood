# 3. Технический аудит Terra Pizza

## 3.1. Общая информация

**Название:** Terra Pizza
**Адрес:** https://terrapizza.by/

Ресурс представляет собой веб-сайт сети ресторанов, позволяющий пользователю ознакомиться с меню и оформить заказ.

Основной пользовательский сценарий:

**Главная → Меню → Категория → Товар → Корзина → Оформление заказа.**

Также пользователь может получить информацию о ресторанах и доступных вариантах получения заказа.

---

## 3.2. Архитектура и логика

Архитектура сайта построена по классической клиент-серверной модели.

Клиентская часть отвечает за:

* отображение страниц;
* навигацию;
* отображение меню;
* работу интерактивных элементов;
* изменение состояния корзины;
* отправку данных пользователя.

Серверная часть отвечает за:

* обработку запросов;
* получение информации о товарах;
* работу с корзиной;
* обработку данных заказа;
* взаимодействие с базой данных.

Основная логика заказа:

1. Пользователь открывает меню.
2. Выбирает категорию.
3. Открывает карточку товара.
4. Добавляет товар в корзину.
5. Изменяет количество товаров.
6. Переходит к оформлению.
7. Заполняет необходимые данные.
8. Выбирает способ получения.
9. Подтверждает заказ.

---

## 3.3. Технологический стек

По результатам анализа клиентской части можно выделить:

* HTML5;
* CSS3;
* JavaScript;
* AJAX/Fetch-запросы;
* адаптивную CSS-вёрстку.

В клиентском коде обнаруживаются подключаемые JavaScript-библиотеки и сторонние сервисы.

Технология серверной части непосредственно из клиентского кода определяется не во всех случаях. Поэтому точную серверную технологию без дополнительного анализа нельзя считать достоверно установленной.

---

## 3.4. Анализ HTTP-запросов

При загрузке сайта обнаруживаются следующие основные типы запросов:

| Тип      | Назначение                     |
| -------- | ------------------------------ |
| GET      | загрузка страниц и ресурсов    |
| GET/XHR  | получение данных каталога      |
| GET/XHR  | получение информации о товарах |
| POST/XHR | передача данных формы          |
| POST     | операции, связанные с заказом  |

Пример структуры исследованного запроса:

| Параметр     | Значение         |
| ------------ | ---------------- |
| Метод        | GET              |
| Тип          | Fetch/XHR        |
| Статус       | 200 OK           |
| Content-Type | application/json |
| Назначение   | получение данных |

Для передачи пользовательских данных используются HTTP-запросы с параметрами или телом запроса.

---

## 3.5. Семантические элементы HTML5

В ходе анализа страницы были обнаружены следующие семантические элементы:

| Элемент   | Количество | Назначение                                   |
| --------- | ---------: | -------------------------------------------- |
| `header`  |          1 | верхняя часть страницы                       |
| `nav`     |          1 | основная навигация                           |
| `main`    |          1 | основной контент                             |
| `section` |          6 | логические разделы                           |
| `article` |          0 | отдельные независимые статьи не используются |
| `aside`   |          0 | отдельная боковая область отсутствует        |
| `footer`  |          1 | нижняя часть страницы                        |
| `form`    |          2 | формы ввода данных                           |

Основная структура страницы является смешанной: семантические элементы используются совместно с `div`.

---

## 3.6. Div-вёрстка

Значительная часть интерфейса реализована с помощью `div`.

Примеры семантически понятных классов:

* `.header`
* `.menu`
* `.menu-item`
* `.product`
* `.product-card`
* `.cart`
* `.footer`

Использование подобных классов позволяет логически разделить структуру интерфейса даже в тех местах, где HTML-элементы сами по себе не отражают назначение блока.

---

## 3.7. Адаптивность

Ресурс адаптирован для различных размеров экрана.

В CSS используются media-запросы вида:

```css
@media (max-width: ...)
```

При уменьшении ширины экрана:

* изменяется расположение элементов;
* количество товаров в строке уменьшается;
* навигация перестраивается;
* изменяется размер отдельных элементов;
* интерфейс становится пригодным для мобильного устройства.

## 3.9. Cookies и локальное хранилище

В Application → Storage обнаруживаются:

* Cookies;
* Local Storage;
* Session Storage.

Cookies используются для хранения информации, необходимой для функционирования сайта и сохранения состояния пользовательской сессии.

Local Storage может использоваться для хранения клиентского состояния.

Session Storage используется для данных, связанных с текущей сессией браузера.

# 8. Функциональности для CampusFood

## 8.1. Высокий приоритет

### Регистрация и авторизация

Пользователь должен иметь возможность создать аккаунт и войти в систему.

### Просмотр заведений

Пользователь выбирает доступное университетское заведение.

Меню разделяется на категории.

* изображение;

* цена;

Пользователь может:

* добавить товар;
* изменить количество;
* удалить товар;
* увидеть общую стоимость.

### Выбор места самовывоза

Пользователь выбирает место, где будет получать заказ.

### Выбор времени получения

Пользователь выбирает доступный временной интервал.

### Оформление заказа

После подтверждения создаётся заказ с уникальным номером.

### Статус заказа

Предлагается следующая последовательность:

**Создан → Принят → Готовится → Готов к выдаче → Выдан.**

# 12. Вывод

В результате технического и функционального анализа были рассмотрены три существующих веб-ресурса ресторанной тематики: Terra Pizza, GARAGE food&coffee и Do.Donerr.

Все рассмотренные ресурсы используют клиент-серверную архитектуру и современные средства веб-разработки, включая HTML5, CSS и JavaScript. В интерфейсах используется комбинация семантических HTML5-элементов и `div`-элементов с CSS-классами.

Исследованные сайты поддерживают адаптивное отображение, используют Cookies и механизмы клиентского хранения, а также подключают сторонние инструменты аналитики и маркетинга.

Функциональный анализ показал, что основными компонентами подобных систем являются каталог товаров, категории, карточка товара, корзина и оформление заказа.

Для CampusFood основными функциями определены регистрация и авторизация пользователя, просмотр меню, формирование корзины, выбор места и времени самовывоза, оформление заказа и отслеживание его статуса.

При этом спецификой CampusFood является ориентация на университетскую среду и **самовывоз без доставки**, что позволяет упростить архитектуру проекта и сосредоточиться на процессе заказа и выдачи еды в учебном заведении.

## Приложение В. Ограничения исследования

Результаты технического анализа клиентской части не всегда позволяют однозначно определить серверную технологию и внутреннюю структуру базы данных. Поэтому серверные технологии, которые невозможно достоверно определить через доступные клиентские инструменты, не рассматриваются как установленные факты.

Показатели Lighthouse зависят от состояния сети, браузера, устройства, нагрузки сервера и времени проведения теста.
